# Work-order failure classifier: rules vs TF-IDF vs an LLM, on wording they have and have not seen

[![tests](https://github.com/devpatram/workorder-failure-classifier/actions/workflows/ci.yml/badge.svg)](https://github.com/devpatram/workorder-failure-classifier/actions/workflows/ci.yml)
![Python](https://img.shields.io/badge/python-3.11%20%7C%203.12-blue)
![License: MIT](https://img.shields.io/badge/license-MIT-green)

Maintenance work orders are free text: `brg on CV-3 running hot, monitoring`. Reliability work needs them counted by
**which component failed and how** (bearing / overheating). This repo compares three ways to do that and scores them
the way it matters in practice: on notes written the way the training data was written, and on notes from a site
that writes differently ("pillow block" for a bearing, "weeping" for a leak).

> All work orders here are made up, generated by `scripts/make_data.py` with exact labels.

## The three methods

| Method | How it works | What it is good at |
| --- | --- | --- |
| Keyword rules | A word list per label, written from the training notes. No match means no label. | Exact and explainable on known wording; silent, not wrong, on new wording. |
| TF-IDF + logistic regression | Word and character n-grams, one model for the component and one for the failure, trained on 240 notes. | Typos and abbreviations close to known words. Optional confidence floor sends unsure notes to review. |
| LLM + validation | The model gets the taxonomy and must answer in JSON with the words from the note that show its answer. The answer is used only if both labels are in the taxonomy, the pair exists (a sensor cannot leak) and the quoted words are really in the note. Otherwise the note goes to a person. | New wording. |

The labels: 8 components (bearing, belt, motor, hydraulic hose, seal, sensor, gearbox, coupling), 8 failure modes,
and the 26 pairs that make sense.

## Results

Test set: 120 notes, 60 with wording seen in training and 60 with wording that never appears in training. The LLM is
`Qwen/Qwen2.5-1.5B-Instruct`, run locally on a 2-core CPU with greedy decoding. Full table: [`eval/results.md`](eval/results.md).

| Method | Seen wording: both labels right | New wording: both labels right | New wording: labeled automatically | New wording: right when labeled |
| --- | --- | --- | --- | --- |
| Keyword rules | 100% | 0% | 0% | n/a |
| TF-IDF + logistic regression | 100% | 7% | 100% | 7% |
| TF-IDF, review below 0.6 confidence | 82% | 0% | 0% | n/a |
| LLM + validation | 72% | 43% | 82% | 53% |
| **Keyword rules, then the LLM for the rest** | **100%** | **43%** | **82%** | **53%** |

What it shows:

- **Seen wording is easy by construction.** Rules written from the training words get every one right. That proves the
  baselines work, not that they are good.
- **New wording is where methods differ, and how they fail matters.** The rules go silent (nothing labeled). TF-IDF
  labels everything and gets 7% right: confidently wrong. With a 0.6 confidence floor it sends every new-wording note to
  review instead, which is safer but labels none.
- **The LLM handles new wording far better (43% fully right), but validation is not correctness.** 20 of 120 answers
  failed validation and went to a person, mostly because the model copied the note's word ("v-belt", "worn") instead of
  a label. Another 31 passed validation and were still wrong. Validation catches answers that cannot be right; it does
  not catch plausible wrong ones, so a person still reviews.
- **The best setup combines them.** Rules first, where they are exact, and the model only for what the rules cannot
  label: 100% on seen wording, 43% on new, 72% overall, with model calls on half the notes.

Next steps: a larger model (`--llm gemini`), a few examples in the prompt that map common synonyms to labels, and a
confidence or second-opinion check before an answer is stored without review.

The data is made up by one generator, so real work orders will be messier. Treat these numbers as a demonstration of
the method, not a benchmark.

## Tests

`pytest -q` (CI on Python 3.11 and 3.12): the taxonomy, the data (labels valid, every pair in training, the new-wording
split, regeneration gives identical files), the keyword rules, TF-IDF on known wording and its confidence floor, the
prompt, JSON parsing, every validation failure, the cascade (rules first, model only for the rest, answers cached),
and a scripted model in place of a real one.

## Run it

```bash
pip install -r requirements-dev.txt
pytest -q
python eval/run_eval.py                                 # rules and TF-IDF, seconds
pip install torch transformers
python eval/run_eval.py --llm local                     # plus Qwen2.5-1.5B-Instruct (about 15 minutes on a 2-core CPU)
python eval/run_eval.py --llm local --model <hf-id>     # any Hugging Face chat model
pip install google-genai
python eval/run_eval.py --llm gemini                    # Gemini via GOOGLE_CLOUD_PROJECT or GOOGLE_API_KEY
```

Results go to `eval/results.md` and every prediction, with the model's raw reply, to `eval/predictions.csv`.

## Layout

```
wofc/
  taxonomy.py   components, failure modes, the valid pairs
  keywords.py   baseline 1
  ml.py         baseline 2
  llm.py        the prompt, JSON parsing, validation, the cascade; local and Gemini models
scripts/make_data.py   the made-up labeled data (fixed seed)
eval/run_eval.py       scoring by wording, results.md, predictions.csv
```
